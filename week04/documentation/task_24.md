# Task 24 — Допустимые переходы состояний тестового запуска

**Дата:** 2026-10-16. **Начать реализацию только после слияния контракта в `main`.** Это новая Python Core-задача, не продолжение и не пересдача Task 23.

## Зачем именно это задание

Ранее ты уверенно применял ранний `return` в отдельных функциях, но при объяснении нескольких ветвей выполнения иногда путался. Здесь нужно **связать две функции, отслеживать текущее состояние и остановиться на первом неправильном действии**. В отличие от Tasks 20/23, это **не подсчёт по словарю**.

Ориентир по времени — примерно 35–60 минут, **не дедлайн и не критерий PASS**. Цель — Python Core: функции, параметры, возвращаемые значения, `if/elif/else`, цикл, `enumerate`, локальное состояние, ранний `return`. Эти конструкции уже встречались; новой синтаксической конструкции не требуется. Неизвестную *идею* переходов состояний объясняем здесь.

**Что такое переход состояний:** одна и та же команда может быть допустима или недопустима в зависимости от текущего состояния. Например, дверь можно закрыть, если она открыта, но команда «закрыть» для уже закрытой двери не меняет состояние и может считаться ошибкой. Это только иллюстрация идеи; реализацию задачи она не диктует.

## Файлы и функции

Создай **один файл** `week04/solutions/python_core_24.py` с двумя функциями и указанными сигнатурами:

```python
def next_state(state: str, command: str) -> str | None:
    ...

def check_scenario(commands: list[str]) -> tuple[str, int | None]:
    ...
```

### 1. `next_state(state, command)` — один переход

Есть ровно четыре допустимых состояния:

- `"IDLE"` — запуск ещё не начат;
- `"ACTIVE"` — выполнение идёт;
- `"PAUSED"` — выполнение приостановлено;
- `"DONE"` — выполнение завершено.

Команды — строки. **Допустимыми являются только эти сочетания:**

| Текущее состояние | Команда | Новое состояние |
| --- | --- | --- |
| `"IDLE"` | `"START"` | `"ACTIVE"` |
| `"ACTIVE"` | `"PAUSE"` | `"PAUSED"` |
| `"PAUSED"` | `"RESUME"` | `"ACTIVE"` |
| `"ACTIVE"` | `"FINISH"` | `"DONE"` |

- Для перечисленной пары функция возвращает строку **нового** состояния.
- **Во всех остальных случаях** возвращает `None`: неверная команда, команда не в том состоянии или любая команда после `"DONE"`. Например, `"FINISH"` из `"PAUSED"` недопустима.
- Сравнение строгое, с учётом регистра и пробелов: `"start"`, `"START "` и `""` не являются `"START"`.
- `state` по контракту всегда одна из четырёх названных строк. Проверять типы аргументов, произвольные состояния и выбрасывать исключения **не нужно**.

### 2. `check_scenario(commands)` — последовательность переходов

`commands` — **список строк**, содержащий команды по порядку. Внутри могут быть любые строки, в том числе неизвестные команды.

- Перед первой командой состояние равно `"IDLE"`.
- Обрабатывай команды **по порядку**, для каждого шага определяя допустимость перехода **через вызов `next_state`**. Это обязательная композиция функций; не дублируй всю таблицу переходов во второй функции.
- При **первой недопустимой** команде немедленно завершай проверку и возвращай кортеж `(state, index)`, где:
  - `state` — состояние **непосредственно перед ошибочной командой**;
  - `index` — индекс ошибочной команды в списке (с нуля).
- Если **все команды допустимы**, верни `(final_state, None)`, где `final_state` — состояние после последней команды.
- Завершать сценарий командой `"FINISH"` **не обязательно**: любая последовательность допустимых переходов считается корректной, даже если осталась в `"IDLE"`, `"ACTIVE"` или `"PAUSED"`.
- Пустой список считается корректной последовательностью без переходов: результат `("IDLE", None)`.
- После `"DONE"` **никакие дальнейшие команды не допускаются**, включая повторное `"FINISH"` или `"START"`.
- Запрещено изменять `commands`, печатать результат, использовать глобальное изменяемое состояние или внешние библиотеки. Исключения при недопустимой команде **не выбрасываются** — ошибка выражается возвращаемым значением.

## Примеры входа и выхода

| Вызов `check_scenario(...)` | Результат | Почему |
| --- | --- | --- |
| `[]` | `("IDLE", None)` | Команд не было |
| `["START"]` | `("ACTIVE", None)` | Допустимая незавершённая последовательность |
| `["START", "PAUSE", "RESUME", "FINISH"]` | `("DONE", None)` | Все переходы допустимы |
| `["PAUSE"]` | `("IDLE", 0)` | Нельзя приостановить то, что не запускалось |
| `["START", "PAUSE", "FINISH"]` | `("PAUSED", 2)` | `"FINISH"` недопустима из `"PAUSED"` |
| `["START", "FINISH", "START"]` | `("DONE", 2)` | После завершения никакие команды не допускаются |
| `["START", "UNKNOWN"]` | `("ACTIVE", 1)` | Неизвестная команда на втором шаге |

Для `next_state`:
- `next_state("IDLE", "START")` → `"ACTIVE"`;
- `next_state("PAUSED", "FINISH")` → `None`;
- `next_state("DONE", "START")` → `None`.

Примеры **не исчерпывают контракт**: проверяются все разрешённые сочетания, первая ошибка и неизменность входного списка.

2. Отправь **один файл** `week04/solutions/python_core_24.py` в отдельной ветке и PR.
3. В чате кратко объясни, **что означает `None` в каждой из функций** и **почему при ошибке возвращается предыдущее состояние**. По итогам ревью будет не более двух вопросов на фактическое выполнение и состояние переменных.

**Собственные pytest-тесты, файл тестов, лог pytest, CLI, работа с файлами и новый учебный отчёт не требуются.** При желании проверяй функцию вручную. Ассистент при доступной среде может выполнить дополнительные проверки **только по этому контракту**; о фактически выполненных проверках и результатах скажет отдельно.

## Критерии PASS — неизменяемые

1. Обе функции соответствуют сигнатурам и всему изложенному поведению на допустимых входных типах и состояниях.
2. `check_scenario` использует `next_state` для проверки переходов, сохраняет состояние до первой ошибки, возвращает индекс **первой** ошибки и не обрабатывает последующие команды после неё.
3. Код не изменяет исходный список, не использует внешние библиотеки, глобальное изменяемое состояние или `print`.
4. Решение предоставлено через PR одним файлом; ученик способен объяснить договорённый смысл двух возвращаемых значений и ход выполнения на одном конкретном примере. Подсказки оцениваются **отдельно** от функциональной правильности.

Во время ревью **нельзя** добавлять новые обязательные команды, поддержку ошибочных типов аргументов, обработку исключений, pytest или иной алгоритмический критерий, отсутствующий в этом документе. Рекомендации по `docs/CODE_STYLE.md` разделять с функциональными дефектами: косметика не является основанием для отказа в PASS, если поведение удовлетворяет контракту.
