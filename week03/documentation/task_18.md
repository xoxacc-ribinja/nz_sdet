# Task 18 — Retry policy и список проблемных тестов

## Цель и уровень

Закрепить проектирование pytest-тестов по письменному контракту (часть A, ~60%) и самостоятельную обработку списка словарей (часть B, ~40%). Это **повторение**: новых обязательных возможностей Python или pytest нет.

Используются уже знакомые `if`, циклы, списки, словари, `isinstance`, `.get()`, `ValueError`, `assert`, `pytest.raises`, `@pytest.mark.parametrize`. Для решения части B не нужны `set`, `Counter`, `mock` и новые библиотеки.

Работай из корня репозитория `nz_sdet`. Не меняй исходный код части A.

## Часть A — SDET: тесты политики повторного запуска

Исходный файл: `week03/input_files/retry_policy.py`.

Функция:

```python
def should_retry(status, attempt, max_attempts):
    ...
```

**Контракт (источник истины):**

- `status` — одна из строк `'PASSED'`, `'FAILED'`, `'SKIPPED'`, `'ERROR'`. Регистр важен.
- `attempt` — номер уже завершённой попытки; `max_attempts` — максимальное число попыток **включая первую**.
- Оба числовых параметра должны быть `int` (но не `bool`), причём `1 <= attempt <= max_attempts`.
- Если статус `'FAILED'` или `'ERROR'` и `attempt < max_attempts`, вернуть `True`.
- В остальных корректных случаях вернуть `False`.
- При недопустимом статусе, типе или значении числовых параметров — `ValueError`.

Примеры по контракту:

| Вызов | Ожидаемый результат |
| --- | --- |
| `should_retry('FAILED', 1, 3)` | `True` |
| `should_retry('ERROR', 2, 3)` | `True` |
| `should_retry('FAILED', 3, 3)` | `False` |
| `should_retry('PASSED', 1, 3)` | `False` |
| `should_retry('SKIPPED', 1, 3)` | `False` |
| `should_retry('FAILED', 0, 3)` | `ValueError` |
| `should_retry('FAILED', True, 3)` | `ValueError` |
| `should_retry('FAILED', 4, 3)` | `ValueError` |

**Задание:** создай `week03/solutions/test_retry_policy.py` и напиши pytest-тесты, проверяющие контракт независимо от реализации.

Обязательные группы проверок:
1. Повторный запуск для `FAILED` и `ERROR`, пока попытки остаются.
2. Отсутствие повторного запуска для `PASSED`, `SKIPPED` и на последней попытке.
3. Недопустимый статус (в том числе неправильный регистр).
4. Невалидные `attempt` и `max_attempts`: ноль, `bool`, `attempt > max_attempts`. Допускается параметризация.

Исходная функция может содержать дефект. **Не исправляй её и не подгоняй ожидаемые результаты под реализацию.** Объясни найденное расхождение с контрактом, если оно есть.

## Часть B — Python Core: список проблемных тестов

Создай `week03/solutions/python_core_18.py` и самостоятельно реализуй:

```python
def extract_problem_tests(results: list[dict]) -> list[str]:
    ...
```

**Контракт:**

- `results` — список словарей; пустой список допустим.
- Каждый словарь обязан содержать:
  - `'name'`: непустую строку (`''` недопустимо; пробелы сами по себе не обрезаем);
  - `'status'`: одну из строк `'PASSED'`, `'FAILED'`, `'SKIPPED'`, `'ERROR'`.
- Дополнительные ключи в словаре разрешены и игнорируются.
- Верни **новый список имён** тех тестов, у которых статус `'FAILED'` или `'ERROR'`.
- Если имя встречается несколько раз, добавь его **только один раз**, в порядке **первого проблемного появления**. Успешная запись того же имени не мешает добавить его позже, если появится `FAILED` или `ERROR`.
- Если проблемных тестов нет, верни `[]`.
- Если `results` не список, элемент не словарь, отсутствует обязательный ключ или значение недопустимо — `ValueError`.
- Не изменяй входной список и вложенные словари.
- Не использовать внешние библиотеки и `collections.Counter`; `set` не обязателен.

Пример:

```python
results = [
    {'name': 'login', 'status': 'PASSED'},
    {'name': 'checkout', 'status': 'FAILED'},
    {'name': 'login', 'status': 'ERROR'},
    {'name': 'checkout', 'status': 'ERROR'},
    {'name': 'profile', 'status': 'SKIPPED'},
]
# Ожидается ['checkout', 'login']
```

Создай `week03/solutions/test_python_core_18.py` и проверь:
1. Смешанные статусы и порядок имён.
2. Повторяющиеся имена и отсутствие дубликатов в ответе.
3. Пустой список и набор без проблемных тестов.
4. Невалидные входные данные (как минимум неверный тип списка, запись без `name`, неверный `status`).
5. Отсутствие мутации входных данных.

## Сдача и критерии PASS

Запусти из корня репозитория:

```bash
python -m pytest week03/solutions/test_retry_policy.py week03/solutions/test_python_core_18.py -v
```

В PR добавь:
- `test_retry_policy.py`;

- `test_python_core_18.py`;
- команду запуска и результат (можно в описании PR; отдельный лог не обязателен);
- краткое объяснение выбора тестов и того, где понадобилась документация или помощь.

**PASS**, если:
- Тесты части A проверяют все четыре перечисленные группы сценариев и используют ожидания из контракта; обнаруженный дефект исходного файла корректно объяснён. Красные тесты из-за дефекта исходной функции **не препятствуют PASS**.
- Функция части B соблюдает весь указанный контракт; собственные тесты части B проходят.
- Автор может самостоятельно объяснить выбор входных данных, проверку валидации и способ удаления повторов.
- Никаких дополнительных требований или обязательных инструментов сверх этого документа в ходе проверки не вводится.

**Ограничение:** не переписывай исторические задания и не исправляй `retry_policy.py` ради зелёного лога. Работаем в отдельной ветке, сдаём через PR.
