# Roadmap: Python → SDET

Дорожная карта по направлениям, без фиктивных сроков и обещаний готовности к найму.

| Направление | Текущее состояние | Следующее проверяемое умение |
| --- | --- | --- |
| Python Core | Практика на обработке данных, функциях и коллекциях; требуется повторение | Решать небольшие задачи без подсказок, находить собственные ошибки |
| pytest | Освоены базовые тесты, `raises`, `parametrize`, простая `fixture` | Самостоятельно проектировать тесты по контракту и объяснять границы |
| Git / code review | Есть история Git и опубликованный репозиторий | Работать через ветки, осмысленные коммиты и PR |
| REST API testing | Впереди | Проверять статус, тело, схему и негативные сценарии |
| UI automation / Playwright | Впереди | Создать поддерживаемые UI-тесты |
| CI | Впереди | Запускать тесты автоматически и разбирать ошибки |
| SQL | Впереди | Проверять данные запросами |
| Технический английский | Сквозная практика | Объяснять код, тест-дизайн и решения на английском |
| Портфолио / интервью | Постепенно | Показывать самостоятельные работы и обсуждать компромиссы |

## Дополнительные решения 2026-10-11

- Bug Investigation — регулярные задания по самостоятельному поиску и устранению дефектов с фактической проверкой тестами.
- Небольшие фрагменты чужого кода — только эпизодически, не в ущерб самостоятельному программированию.
- Недельный тематический фокус не вводить. **Новый ориентир — 12 часов в неделю**, по решению ученика от 2026-10-11; распределение по дням свободное.

## Корректировка практики с 2026-10-11

- **Актуальный ориентир нагрузки — 12 часов в неделю** с 2026-10-11 вместо прежних 3–5; пропуски не создают обязательства нагонять часы.
- Вместо серий почти одинаковых задач — знакомые Python/pytest-инструменты в разных постановках, с акцентом на самостоятельный выбор подхода.
- Короткие вопросы на воспроизведение знаний и интервальное повторение через несколько дней.
- Отдельно оценивать корректность решения и степень самостоятельности (без помощи / после подсказки / после разбора).
- В отчётах разделять кодирование, инженерные активности и организационные потери времени; не смешивать их в одну метрику практики.

## Принципы перехода

- Не добавлять новый инструмент только ради «широты стека».
- Следующий этап открывать после проверки навыков на новой задаче без готового шаблона.
- Намеренно падающий тест, который выявляет нарушение контракта, не считать ошибкой тестирования.
- Отдельно различать учебный прогресс, готовность к интервью и реальный опыт SDET.

Распределение тем и критерии корректируются по результатам практики; изменения фиксируются в `DECISIONS.md`.

## Приоритеты после интервью 2026-10-13

Диагностическое интервью по вакансии Automation Tester (Auckland) показало разрыв между базовым тестовым мышлением и практической AutoQA-подготовкой. **Это приоритеты следующей практики, не новые дедлайны и не одномоментное увеличение нагрузки.**

1. **SQL для QA:** выборки, фильтры, `JOIN`, агрегация и проверка данных приложения; результат — написать и объяснить запрос на незнакомом наборе таблиц.
2. **API testing на Python/pytest:** запросы, статусы, контракт ответа, авторизация, негативные проверки, фикстуры и управляемые тестовые данные; результат — воспроизводимый небольшой набор API-тестов.
3. **Playwright + Python:** селекторы, ожидания, изоляция тестов, проверки состояния и диагностика падений; результат — самостоятельно написать и запустить UI-сценарии, а не только описать их.
4. **CI, flaky tests, bug investigation:** артефакты прогона, логи, trace, сравнение окружений, гипотезы и воспроизведение; результат — расследовать нестабильность и обосновать первопричину.
5. **Test management и интервью:** карты покрытия, связь требований/тестов/дефектов, риск-ориентированный тест-план, короткий статус релиза и интервью без подсказок; результат — подтверждать решения артефактами и точным объяснением.

Порядок можно адаптировать к зависимости навыков и фактическому времени; не считать эти пять пунктов пятью параллельными курсами. Python Core — средство разработки и анализа, а не бесконечный самостоятельный цикл похожих упражнений.

### Эффективность проектирования тестов

- Вместо механического полного перебора: контракт → карта классов/границ/связей → риски → небольшой диагностически ценный набор → реализация.
- Не плодить комбинации ради количества; каждую существенную комбинацию обосновывать отдельным риском или возможным дефектом. При необходимости использовать pairwise только после объяснения ограничения этого метода.
- Упрощать данные через фабрики/фикстуры/параметризацию, изучая инструменты постепенно; не превращать генератор данных в основную задачу, если цель — тест-дизайн.
- При ревью оценивать полноту требований, информативность сценариев, самостоятельность и время на механический ввод отдельно. Новые PASS-критерии не добавлять задним числом.
