# Decisions

Короткий журнал решений по обучению и организации репозитория. Новые записи добавлять с датой и причиной.


## 2026-10-13 — Перенастройка AutoQA-траектории по диагностическому интервью и Task 20

**Причина:** интервью по вакансии Automation Tester (Auckland) выявило провалы в SQL и Playwright/Selenium, недостаточную глубину диагностики и планирования; Task 20 показала избыточные трудозатраты на ручное оформление похожих тестовых комбинаций (запись автора — более 2 часов на тесты B, около 30 минут на попытки генерации и примерно 1,5 часа ручного оформления; оценки приблизительные). Множество строк тестовых данных не считать самоцелью.

**Уточнение учеником 2026-10-13 (приоритет над первоначальной формулировкой): до ноября 2026 основной фокус сохраняется на Python Core.** SQL, API-тесты, Playwright, CI/диагностика и test management — последующая прикладная AutoQA-траектория, не ближайшие обязательные задания. Не вводить одновременно несколько неизвестных инструментов без обучения. Сохранять ориентир 12 часов/неделю и гибкое расписание; прежние 60/40 и 25/50/25 — исторические пропорции, **не действующие жёсткие квоты**. Новое распределение по часам не навязывать до наблюдения за реальным темпом.

**Решение — тест-дизайн:** до реализации ученик составляет краткую карту покрытия (правила, значимые классы эквивалентности, границы, приоритетные комбинации и риски), затем выбирает **минимальный обоснованный набор** проверок. Не требовать декартова произведения всех параметров без доказанной необходимости. Для сокращения дублирования обучать сначала простым фабрикам тестовых данных, `parametrize` и fixture, затем при необходимости генеративным/property-based подходам. Не отдавать ученику готовый чек-лист: авторство сценариев остаётся его задачей. Измерять качество независимой способностью объяснить, какой дефект ловит каждая группа проверок, а не количеством кейсов. Не снижать полноту требований контракта и не пересматривать PASS Task 20.

**Решение — обучение вместо зацикленного повторения:** новый материал объяснять до задания; далее короткая самостоятельная практика, содержательное ревью и перенос в новый контекст. Цель — устойчивое извлечение знаний: закрыть пример, воспроизвести без подсказки, проверить через ~час и позже; при ошибке применять минимальную подсказку и сразу повторять самостоятельно. Интервальные проверки короткие; не занимать ими большинство времени. Навык считать удержанным только при отсроченном самостоятельном применении. Для новых заданий — контракт и PASS заранее в GitHub. Сложность наращивать по одной инженерной оси, избегая марафонов ручного набора тестовых данных.

**Решение — обратная связь:** жёсткая по сути и доказательная: сначала дефекты, пробелы, уровень самостоятельности, соответствие найму и конкретная цена ошибки. Не добавлять комплименты за обычные правильные ответы; выдающиеся сильные стороны отмечать только по повторяемым независимым доказательствам. Не подменять требовательность грубостью, необоснованным приговором или задним числом изменёнными критериями. Чётко различать наблюдалось / не проверялось / не смог выполнить.

**Проверка эффекта:** сначала через короткие новые задачи Python Core с отсроченным независимым решением, позднее — реальные задачи SQL, API и UI, независимое расследование дефектов и интервью по аналогичной вакансии. Не утверждать, что освоение инструмента или готовность к найму подтверждены до выполненной практики.

## 2026-10-12 — Защита в чате, краткий итог в GitHub

**Решение:** начиная с Task 19 ученик объясняет тест-дизайн, найденные дефекты и алгоритм решения в диалоге с ассистентом. Не требовать отдельного сочинения или конспекта от ученика в описании PR. После защиты ассистент готовит краткую проверяемую запись в `LEARNING_LOG.md` (при необходимости обновляет `PROJECT_STATE.md`) через отдельную ветку и документационный PR. Запись включает ссылку на решение, фактические тестовые результаты, выводы, ошибки, самостоятельность и статус. Не копировать полную стенограмму чата; не утверждать, что тесты запущены, без запуска. Учебный PR содержит код и доступные свидетельства проверки, слияние остаётся за владельцем.

**Task 19:** исходный контракт и PASS-критерии не меняются; объяснение дефекта части A и алгоритма части B проводится в чате и фиксируется итогом в GitHub после защиты. Отдельное описание в PR #17 не требуется. Документационный PR сам по себе не означает PASS.

**Причина:** ученик хочет тратить время на понимание и защиту решений, а не дублировать объяснения в PR и переписывать беседу.

## 2026-10-12 — Самостоятельный выбор тестовых сценариев в новых заданиях

**Решение:** начиная с Task 20, при выдаче заданий на тест-дизайн публиковать полный, однозначный контракт поведения и заранее согласованные общие критерии PASS, **но не перечислять обязательные группы проверок или готовый чек-лист тест-кейсов**. Ученик самостоятельно определяет сценарии, границы, негативные случаи и риски. Во время ревью указывать упущенные проверки, обосновывая их опубликованным контрактом; не вводить новые требования и не менять критерии PASS задним числом. Разбирать полноту тест-дизайна и самостоятельность отдельно. **Task 19 не изменять.**

**Причина:** готовый список тестовых групп подсказывает решение и мешает проверять перенос навыка на новую задачу без подсказок.

## 2026-10-12 — Ежедневная публикация NZ DAILY в GitHub

**Решение:** NZ DAILY за предыдущий день формируется ежедневно по расписанию (ориентир — утро, 08:00 по местному времени пользователя, гибкое окно) и предлагается к публикации в публичном репозитории через отдельную ветку и Pull Request. Если ученик **явно просит конкретный отчёт только в чате**, исключение относится только к этому отчёту; остальные ежедневные отчёты публикуются по обычному процессу. При недостатке данных указывать их отсутствие, не выдумывать часы или результаты. Отчёты содержат только обезличенный технический контекст. Автоматизация создаёт PR, но не утверждает, что изменения слиты в `main`. Это **расписание отчётности**, не обязательный график занятий и не требование наверстывать часы.

**Причина:** ученик уточнил, что прежняя формулировка «по запросу» и распространение «только в чате» на несвязанный отчёт не соответствуют ожидаемому процессу.

## 2026-10-12 — Разнообразие контекстов учебных задач

**Решение:** чередовать рабочие, игровые (геймдев) и нейтральные сценарии при обучении Python Core, pytest, тест-дизайну и отладке. Проверять перенос одного и того же навыка между предметными областями, а не воспроизведение знакомых примеров из предыдущих Tasks. Использовать игровые контексты эпизодически (инвентарь, экономика, сохранения, квесты и т. п.), без обязательной квоты и без выделения геймдева в отдельный курс. Не повышать сложность синтаксиса без предварительного объяснения. При разборе ответов различать знание правила, применение к примеру и внимательность при чтении условий.

**Причина:** ученик попросил больше вариативности и сочетание рабочих и игровых сюжетов; повторение почти дословных ситуаций из старых заданий не показывает перенос знаний.

## 2026-10-11 — Bug Investigation и эпизодическое чтение чужого кода

**Решение:** добавить Bug Investigation как регулярный самостоятельный формат: диагностика неизвестного дефекта, чтение traceback и вывода pytest, гипотеза, локализация первопричины, минимальное исправление и проверка запуском тестов. Обнаружить баг и найти его причину — разные навыки. Читать небольшие фрагменты незнакомого кода эпизодически, не вместо основной практики программирования. Не вводить недельный тематический фокус или расписание по дням. Не делать изучение исходников pytest, внешние open-source PR и отдельный DEBUG_NOTES обязательными.

**Нагрузка:** ученик установил **12 часов в неделю** с 2026-10-11 вместо прежних 3–5. Это ориентир без обязательного расписания по дням; пропуски не нужно компенсировать, а качество самостоятельной практики по-прежнему оценивается отдельно от количества часов.

**Причина:** явное решение ученика после критического разбора предложений от другой ИИ-системы.

## 2026-10-11 — Перераспределение учебной нагрузки после Task 18

**Решение:** оставить ориентир **3–5 часов в неделю**, не увеличивать его ради ускорения. Сократить долю почти идентичных упражнений и использовать знакомые конструкции в новых контекстах. Сохранять ежедневные 3–4 коротких вопроса без написания кода; возвращаться к пройденным темам с интервалом в несколько дней. При проверке отдельно фиксировать правильность решения и самостоятельность воспроизведения: без подсказок, после наводящего вопроса, после подробного объяснения. Различать непосредственное программирование, инженерную работу (тест-дизайн, анализ, ревью, отладка, Git) и организационные потери времени. Не считать устранение организационных ошибок практикой кодирования. Не вводить дополнительные обязательные критерии PASS.

**Причина:** после Task 18 ученик сообщил, что узнаёт и понимает изученные конструкции при объяснении, но испытывает трудности с их самостоятельным воспроизведением. 2026-10-11 на обучение ушло около четырёх часов, из них непосредственное программирование — не более двух; часть времени заняли организационные ошибки. Нужна не большая нагрузка, а лучшая проверка удержания знаний.

## 2026-10-11 — Ежедневные короткие разминки

**Решение:** после первого обращения ученика за день в учебном чате предлагать 3–4 небольших вопроса на понимание ранее пройденных тем (Python Core, pytest, Git, тест-дизайн). Чередовать темы и иногда возвращаться к старым; не превращать разминку в новое обязательное условие PASS и не вводить через неё неожиданные требования к текущему заданию. Если ученик прямо просит сначала завершить текущую работу, не прерывать её вопросами.

**Причина:** проверять усвоение и перенос знаний между задачами, а не только воспроизведение знакомого шаблона.

## 2026-10-11 — Сначала опубликованное задание, затем код

**Решение:** перед началом каждой новой задачи ассистент публикует Markdown-файл задания в `weekXX/documentation/` и предоставляет ссылку. В файле заранее фиксируются контракт, ограничения и критерии PASS. Новые обязательные требования нельзя добавлять во время проверки; изменения возможны только после явного согласования и обновления документа. Новые конструкции Python сначала объясняются, затем используются в практике. Перед заданиями, ревью и изменениями в репозитории ассистент перечитывает соответствующую документацию GitHub.

**Причина:** Task 17 выполнялся без своевременно опубликованного файла задания; требования и объяснения вводились несвоевременно. Необходимо сделать процесс воспроизводимым и исключить повторение проблемы.

## 2026-10-09 — Скрытые проверки после защиты

**Решение:** иногда проверять сданный и защищённый код на заранее не раскрытых входных данных. До защиты конкретные значения не сообщать; после проверки объяснять результат.

**Причина:** оценивать перенос навыка на новые случаи, а не только прохождение известных примеров. Проверки не должны добавлять требований вне согласованного контракта. Нельзя выдавать неисполненный тест за успешно пройденный.
